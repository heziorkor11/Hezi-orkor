# מדרגות כמות למוסכים

ענף `feature/admin-bulk-tiers` מבוסס על ענף PR #9, לא על main. מיועד ל-PR מדורג אל `feature/admin-dashboard`; אין למזג ל-main בנפרד ממנו.

## שימוש
בעלים: `/admin/promotions` → **מדרגות כמות למוסכים**. הגדרת יעד (מק״ט בקטגוריית מארזים או כל קטגוריית מארזים), ספי מספר מארזים ואחוזי הנחה, פעיל/כבוי, פומבי/הצעת מחיר בלבד, וצבירה בין מק״טים לכלל קטגוריה. עובד אינו מורשה לשנות מדרגות, גם אם יש לו הרשאת מבצעים.

אין כללים או הנחות כברירת מחדל. כל שורה היא מספר מארזים / מיכלים כפי שהמוצר נמכר, לא יחידות פנימיות. תכולה מפוענחת רק כשמפורשת בשם; לא מנחשים תכולה או מחיר. הספים ייחודיים, חיוביים ושלמים; הנחות בטווח 0–99.99 ואינן יורדות עם העלייה בכמות. ניתן לכבות כלל בלי מחיקתו.

כלל מוצר גובר על כלל קטגוריה. בצבירה כלל קטגוריה סופר רק מוצרים שמקבלים אותו כלל, לא מוצרים עם כלל מוצר משלהם. נבחר הסף הגבוה ביותר שהושג. הנחה מחושבת ממחיר רגיל כולל מע״מ לאחר override, ללא כפל מבצע: המחיר הנמוך בין המבצע למדרגת הכמות. עיגול לאגורה למחיר יחידה. מחיר חסר נשאר לבירור. אין שינוי לקובצי מחירי הבסיס.

בחנות: רשימת מארזים ודף מוצר מציגים תכולה, בורר מספר מארזים וסכום; הסל, PDF, הודעת הזמנה ורשומת הזמנה משתמשים באותם כללי חישוב. שינוי כמות בסל מחשב מחדש מדרגות לכל המוצרים הזכאים. בהוספה נלקחים בחשבון המארזים שכבר בסל.

במצב הצעת מחיר בלבד אין מחיר כמות אוטומטי (גם בסכומי הסל/PDF); מדרגות ההנחה אינן נכללות ב-public projection. מחיר קטלוג רגיל עדיין עשוי להיות מוצג מחוץ לבורר הכמות. מצב זה אינו מסתיר מחירי בסיס ואינו מבטיח הצעת מחיר מסוימת.

## פנייה חינמית
כפתור **כמות אחרת / הצעת מחיר למוסך** פותח טופס שם/מוסך, מספר מארזים והערה. הפרטים נמצאים רק בזיכרון הטופס; לא נשלחים לשרת או נשמרים באתר/ב-Git. פתיחת WhatsApp היא קישור לעסק הקיים; הלקוח חייב ללחוץ שליחה שם. מנגנון הזמנת PDF הקיים נפרד ולא השתנה למדיניות שמירת פניות.

## אחסון ו-Preview
`bulkRules` הוא חלק ממצב adapter הקיים, נשמר עם audit מי/מתי/ישן/חדש. במצב git — אותו JSON מוצפן, CAS ורשימת ענף מאושרת, ללא שירות חדש. אין שינוי ב-token או חיבור ל-GitHub חי במסגרת פיתוח זה. הכללים נקלטים גם ממסמך ישן ללא השדה. מצב preview ממשיך להיות ephemeral עם קבלת שינויים בצד הדפדפן למניעת פער בין מופעים. פרטי לקוחות לעולם אינם נשמרים ב-Git בריפו הציבורי.

ענף ה-Preview החדש מותר במפורש בקוד, אבל **אין הפעלה אוטומטית ואין סיסמה בקוד**. לצורך בדיקת admin ב-Vercel נדרשות הגדרות PREVIEW לענף `feature/admin-bulk-tiers` בלבד: `ADMIN_STORAGE=ephemeral`, `ADMIN_PREVIEW_DEMO=1`, `ADMIN_OWNER_USERNAME`, `ADMIN_OWNER_PASSWORD_HASH` (ולפי צורך `ADMIN_EMPLOYEE_USERNAME`, `ADMIN_EMPLOYEE_PASSWORD_HASH`). אותן הגדרות שכבר קיימות רק לענף PR #9 אינן עוברות אוטומטית. לא הוגדרו כאן משתני Vercel/Production חדשים. נדרש אישור להגדרתן בענף החדש; Preview ללא משתנים יישאר fail-closed. לעולם אין להפעיל ephemeral ב-Production.

## אימות
- `node scripts/test-bulk-tiers.mjs`: ספים, אפס כללים, כיבוי, הצעת מחיר, מחירים חסרים, ללא כפל מבצע, העדפת מק״ט, צבירה זכאית.
- `npm run test:admin`: API בעלים, הרשאות עובד, ולידציה, audit, התמדה אחרי restart, הסתרת אחוזים מ-public.
- `npm run build`: בדיקת bundle אמיתי ב-cwd לקריאה בלבד עם fake Git API: שמירת כללים, public projection, SSR מארזים וקליטת הזמנה 2+3 מארזים במחירי בדיקה 100/200 עם 10% → 720 כולל מע״מ. אין שימוש ב-Git API חי בבדיקה.
- בדיקת דפדפן/מגע בפועל לא בוצעה; אין לטעון ש-QA בנייד עבר.


## עיצוב בחירת מתן — Unit value
`/results?category=workshop-packs` מקבל עמוד ייעודי בהשראת `01-unit-value.html`: רקע בהיר, כותרת ״מארז אחד. המחיר ברור.״, כרטיס לבן עם תמונה שלמה, מחיר קטלוג גדול למארז, חלוקה מחושבת ליחידה/לליטר ונתוני תכולה מפורשים. מחיר יחידה אינו הבטחה למחיר קנייה בודדת. בנייד עמודה אחת; מ־640px שתי עמודות ומ־1024px שלוש. כל CSS החדש תחום ל־bulk-unit-page; שאר הקטגוריות ללא שינוי עיצובי.

כמות מספרית וכפתורי +/− מעדכנים סכום כולל מע״מ. קופסת ״הנחת כמות / חסכתם״ קיימת רק כשהמדרגה שהבעלים הגדיר באמת מוזילה את המחיר הנוכחי; החיסכון לעומת מחיר הקטלוג העדכני (כולל מבצע קיים אם יש), עבור הכמות הנבחרת בלבד. ללא כללים — סכום רגיל, אין אחוז או חיסכון מומצאים. מצב הצעת מחיר בלבד ומחיר חסר לא מציגים חיסכון. כבר־בסל מוצג כדי להבהיר צבירה. כל פנייה ל־WhatsApp ממשיכה להיות ללא אחסון פרטי לקוח באתר.

ה-Preview לענף הזה הוגדר בנפרד למצב ephemeral בלבד עם פרטי הבדיקה הקיימים; אין שינוי ב-Production. בדיקות build ו־bundle בודקות גם את העמוד החדש, את היעדר הנחות ברירת מחדל ואת הופעת חיסכון לאחר הגדרת מדרגה בידי הבעלים. בדיקות לוגיקה אינן בדיקת מגע/פיקסלים בדפדפן; נדרש QA בנייד 400px.
